# Review 文档规范

> 本文档是 `docs/review/` 下所有 review 文档（`*.md`）的强制性写作规范。
> Review 文档用于记录代码审查中的发现、修复建议、修复历史。所有 review 文档必须遵守本规范。

---

## 1. 文件位置与命名

- 所有 review 文档存放于 `docs/review/`
- 命名格式：`<模块名>-code-review.md`（例：`ringbuf-code-review.md`）
- 全局视角的跨模块 review：`global-review.md`
- 已废弃的 review 文档可加时间戳保留（例：`depth-code-review-2026-07-03.md`）
- **归档目录**：`docs/review/history/`，用于存放已归档的关闭问题

### 1.1 Review 内容边界

**所有 review 相关内容必须写在 `docs/review/` 下。**
- Review 文档（本章规范下的全部文件）只位于 `docs/review/`，不得散布到 `docs/` 其他地方或其他目录
- 一条规则、一个约定、一个 review policy——如果它属于 review 流程，它的 SSOT 就在 `docs/review/AGENTS.md`
- `docs/plans/` 和 `docs/specs/` 下的设计文档可能被 review 引用（作为"文档仲裁"的依据），但 review 文档本身不写入那里
- 跨模块 review 发现写 `docs/review/global-review.md`，不写进各模块自己的设计文档

---

## 2. review 文档的三大分区

每个 review 文档**必须**按顺序包含以下三个一级分区：

### 2.1 修复历史（Fix History）

- 记录该模块 review 中**已被修复**的问题
- 追加式（append-only），按修复时间倒序或正序皆可
- 每条记录必须包含：问题 ID、问题摘要、修复 commit/branch、修复日期
- **不可删除**已修复的记录（用于审计追溯）
- 不需要"作者建议"字段（已修复，问题已闭环）

### 2.2 现在打开的问题（Open Issues）

- 当前**尚未关闭**的问题，按严重度从高到低排序
- 每条记录**必须**包含以下子分区：
  - **问题描述**（必须）
  - **review 建议**（必须）：review agent 提出的修复建议或方向。创建时由 agent 填写。
  - **作者建议**（可选）：代码作者针对此问题的处理意见或计划。初始为**空**，由作者后续补充。
  - **状态**（必须）：`打开`
  - **严重度**（必须）：🔴 关键 / 🟠 高 / 🟡 中 / 🟢 较低
  - **可重现的失败场景**（必须）
  - **定位**（必须）：文件 + 行号

#### 重要——作者建议为空时的限制

- **作者建议**初始时**必须为空**（留空或写 `（待作者补充）`）
- **任何修复 agent（AI）不得在作者建议为空时对该问题实施修复**
- 修复 agent 只能处理**作者建议已填写**的问题——作者建议是作者对修复方向的确认或决策
- 作者建议不等于 review 建议。review 建议是 agent 的分析结果，作者建议是作者的意图。

#### 字段示例

```markdown
#### review 建议
将 size 上限从 UINT32_MAX/2 降低到 UINT32_MAX/3，或改用 uint64_t 中间加法。

#### 作者建议
（待作者补充）
```

### 2.4 文档仲裁规则（重要）

Reviewer 提出问题前必须自查：**该行为是否已在当前模块的公开文档（`.h` 文件 docstring、`AGENTS.md`、`CLAUDE.md`、`README.md`）中被明确描述？**

- **如果行为已文档化**，则这不是 bug，而是已知设计。reviewer **不得**将该问题列为"现在打开的问题"。
  - 正确做法：若认为文档描述的决策不合理，应先修文档再提 bug，或写入"架构观察"（不在打开问题中记录）。
  - 文档涵盖设计权衡、线程安全约束、已知竞态窗口、边界行为等所有"有意为之"的约定。
- **如果文档承诺了某行为但代码未实现**，这是"文档-代码不一致"。应标记为 `关闭-不适用`（doc 已描述但 reviewer 误判为 bug），并在关闭原因中引用文档位置。
- **如果行为既非文档化、也不影响功能正确性**（如代码整洁、抽取函数），可列为 cleanup 发现，但 reviewer 应在`严重度`上标记为 `🟢 较低`，并注明 `cleanup` 标签。

#### 文档仲裁检查清单（reviewer 发现 finding 前逐一自问）

1. 该行为是否在 `.h` docstring 里有描述？
2. 该行为是否在项目规范（`AGENTS.md` / `CLAUDE.md` / `README.md`）里有约定？
3. 该行为是否是已知的设计权衡（如文档中注明的"非阻塞 emit 不可回滚"）？
4. 如果答案有任何一个是"是" → 这不是 bug，停止。

#### 作者关闭的快捷通道

作者在关闭问题时，若理由为"已文档化 / 设计权衡 / 已知约束"，可直接使用 `关闭-已拒绝` 状态并在关闭原因中引用文档位置，无需额外讨论。

### 2.5 发现分类标签

Reviewer 可以在发现末尾标注类型标签便于归类：

| 标签 | 含义 | 示例 |
|------|------|------|
| `bug` | 代码行为与预期/文档不一致 | release fence + plain store 无同步效果 |
| `cleanup` | 可优化/简化但无功能影响 | 抽取重复 memcpy 块 |
| `doc` | 文档需要更新 | 旧 doc 写 int32_t 而代码已改 uint32_t |
| `test` | 测试覆盖缺口 | 未测 size 超限分支 |
| `design` | 架构层建议 | 改用 uint64_t 消除 size 上限魔数 |

### 2.6 作者仲裁规则（重要）

Reviewer 提出问题后，作者（你）可以通过对话与 reviewer 讨论。如果作者能说服 reviewer 这不是 bug 或不需要修，finding 可以直接关闭。

**关闭流程**：
1. 作者在 `作者建议` 字段中写入你的反驳理由（这是"作者建议"的本来用途——这是你对这个问题的意见）
2. 作者更新 `状态` 为 `关闭-已拒绝`
3. 作者在 `关闭原因` 中引用对话内容或直接写理由
4. 这条 finding **永久保留**在 review 文件中（`关闭-已拒绝` 永不归档）

**规则要点**：
- 作者建议和 reviewer 的 review 建议是**同等有效的意见**——reviewer 认为需要修、作者认为不需要，两者都合法
- 不需要达成一致。作者决策权 override reviewer 建议
- 仲裁结果是 `关闭-已拒绝`，不是 `关闭-不适用`（后者用于 reviewer 自己发现误报）
- 仲裁后的 finding 永远不删除（`关闭-已拒绝` 规则），供以后 review 迭代时参考

**示例**：

```markdown
#### 作者建议
该行为已在 header line 154-157 明确文档化，
peek 的两条路径语义是已知设计，reviewer 已确认。
→ 关闭-已拒绝

#### 关闭原因
文档仲裁：行为已文档化，非 bug。经作者确认。
- 关闭日期: 2026-07-04
- 状态: 关闭-已拒绝
```

### 2.7 现在关闭的问题（Closed Issues）

- 当前**已关闭**、**尚未归档**的问题
- 同一个模组的多条关闭问题在本节集中显示
- 每条记录**必须**包含以下子分区：
  - **问题描述**
  - **状态**（必填）：`关闭-已修复` / `关闭-已拒绝` / `关闭-延期` / `关闭-不适用`
  - **关闭原因**（必填）：
    - `关闭-已修复`：附上修复 commit/branch
    - `关闭-已拒绝`：作者认为无需修复，附理由（如设计权衡、误报、已文档化）
    - `关闭-延期`：附上延期至的版本/里程碑
    - `关闭-不适用`：误报或已修复但不在本 review 范围
  - **关闭日期**（必填）
  - **预计归档日期**（可选）：`关闭-已拒绝` 以外状态，默认一个月后归档
- `关闭-已拒绝` 的条目**永久留在主 review 文件中**，不归档、不删除
- 其他 `关闭-*` 状态，关闭满**一个月**后由 review agent 自动移至历史归档

## 3. 问题 ID 规范

- 每个问题必须有唯一 ID
- 格式：`<模块缩写>-<三位数字>`，例：`RINGBUF-001`、`TIMER-003`
- 同一问题在 review 重做时**必须**保留原 ID，即使严重度变更
- 新发现的问题在已有序列后递增

### 3.1 禁止重复提出已拒绝问题

- **规则**：Reviewer agent 在每次 review 时，**必须**先扫描对应模块 review 文档的"现在关闭的问题"与"修复历史"分区。若发现要提出的问题**实质**已被记录为 `关闭-已拒绝`、`关闭-已修复`、`关闭-不适用` 或 `关闭-延期`，则**不得**重新提出。
- **判定标准**：与历史条目**实质相同**即视为重复——相同的代码位置、相同的根因、相同的修复方向。即使措辞不同、严重度不同、ID 不同，也视为重复。
- **允许例外**：
  1. 原拒绝理由在新代码/新设计中已不再成立（如 API 变更、平台支持变更）
  2. 代码确实回归（之前拒绝的问题再次出现在代码中）
  3. 重新 review 时需明确引用历史条目 ID 并说明"为何重新提出"
- **违反后果**：重复提出已拒绝问题视为 review agent 的失职，会污染 review 文档并浪费作者仲裁时间。Review agent 自动化应至少 grep `关闭-已拒绝` / `关闭-已修复` / `关闭-不适用` / `关闭-延期` 关键词后再撰写新 finding。
- **示例**：若 `BROKER-001` 已 `关闭-已拒绝`（g_broker 无同步读取），后续 reviewer 不应再以"g_broker 存在竞争"为由新增 `BROKER-014`。如确需重新讨论，必须以 `BROKER-001` 原 ID 重新打开，并在 review 建议中说明重开理由。

## 4. 角色与责任

| 角色 | 责任 |
|------|------|
| **Reviewer (review agent)** | 编写 review 文档，提出问题，填写 **review 建议** |
| **作者（代码作者/修复者）** | 阅读问题，填写 **作者建议**，实施修复，更新状态 |
| **维护者** | 处理关闭状态、归档、review agent 自动化 |

### 4.1 reviewer 与作者的分工

| 字段 | 谁写 | 何时写 |
|------|------|--------|
| **review 建议** | review agent | 创建问题时立即填写 |
| **作者建议** | 代码作者（人） | 后续评估后填写。初始为空 |
| **关闭原因** | 代码作者 / 维护者 | 关闭问题时填写 |

**核心规则**：作者建议为空时，任何修复 agent（AI）**不得**对该问题实施修复。作者建议是作者对修复方向的确认。

### 4.2 模块归属规则（重要）

- **每个 review agent 只 review 自己负责的模块**：不得跨模块 review
- 模块与 review agent 的对应关系在 `docs/agents/review/` 下定义（按需要扩展）
- 跨模块的问题发现应写入**全局视角**的 review 文档（命名：`global-review.md`）
- 全局 review 文档同样遵守本规范，但允许记录跨模块的依赖性问题

### 4.3 Reviewer 产出要求

Reviewer 提出问题时**必须**给出 **review 建议**——任何**没有建议**的 review 发现都是不完整的。
**作者建议**由作者填写，初始为**空**——agent 不得自行填充作者建议。

作者在关闭问题时**必须**填写"关闭原因"——任何**没有原因**的关闭都是不规范的。

### 4.4 合同前提保护（Contract-Protected Findings）

**核心定义**：当一个 finding 描述的行为**只在调用方违反文档化 API 前提（precondition）时才会触发**，该 finding 视为"合同前提保护"，不应作为库缺陷处理。

#### 4.4.1 判定标准

一个 finding 满足以下**全部**条件时为合同前提保护：

1. **前提文档化**：相关 API 前提已在**公共头文件**（`*_port.h`、`nanosig_*.h`）的 Doxygen 注释或 `@section 生命周期` 等专门段落中**明确写出**，而非仅散见于 `.c` 文件内注释。
2. **触发条件**：finding 所述问题**仅**在调用方违反该前提时出现——满足前提时行为正确、合理、可证。
3. **未违反前提时的行为**：满足前提时不存在 finding 所述缺陷，无需修改代码即可达成正确行为。
4. **违反前提时**：行为未定义或退化为"用户错误"，库**没有义务**保证正确性。

#### 4.4.2 常见合同前提类型

| 类型 | 例子 |
|------|------|
| **线程串行约束** | "A/B 函数不能并发调用"、"A 必须在 B 之后调用" |
| **生命周期约束** | "connection 生命周期 ≤ signal 生命周期" |
| **状态机约束** | "init 后才能 run"、"run 返回后才能 deinit" |
| **所有权约束** | "调用方持有资源所有权" |
| **回调内禁止操作** | "consume_fn 禁止调用 add/remove" |
| **初始化阶段约束** | "init 必须在 main 线程串行调用"（若文档化） |

#### 4.4.3 处理流程

Reviewer agent 撰写 finding 前**必须**自检：

```
1. 找到相关 API 的公共头文件声明
2. 阅读 @pre / @warning / @attention / @section 等文档段
3. 检查 finding 描述的触发场景是否被任意一条文档化前提覆盖
   ├─ 是 → 标记为"合同前提保护"，按 4.4.4 处理
   └─ 否 → 检查前提是否**应该被文档化**
        ├─ 是（隐含但未写出） → 转交作者，要求先文档化前提，再决定 finding 去留
        └─ 否（无合理前提） → 正常 reporting 为 bug
```

#### 4.4.4 关闭原因模板

合同前提保护的 finding **应**使用 `关闭-已拒绝` 状态，关闭原因采用以下模板：

```markdown
#### 关闭原因
合同前提保护：`{API 名}` 在 `{头文件路径}:{行号}` 已文档化
"{前提原文摘录}"。finding 所述问题仅在调用方违反该前提时出现，
属用户错误而非库缺陷。

- 关闭日期: {yyyy-mm-dd}
- 状态: 关闭-已拒绝
```

#### 4.4.5 反例（不应作为合同前提保护处理）

以下情况**不属于**合同前提保护，应作为真实 finding：

- 前提**未文档化**于公共头（仅在 `.c` 文件注释或口头约定）→ 这是文档缺陷，应单独 reporting
- 违反前提时库**仍可能**触发严重后果（UB、数据竞争、内存安全）→ 即使有合同也值得防御性加固
- 多个 API 共同形成**隐含**前提但**没有任何一处文档化**该前提
- 前提**自相矛盾**或与代码行为冲突（如文档说"线程安全"但代码用了非原子变量）

#### 4.4.6 与现有规则的关系

- **§3.1 禁止重复提出已拒绝问题**：合同前提保护关闭的 finding 受本规则保护，不得以"再次违反合同会怎样"为由重新提出，除非触发场景已根本改变（API 变更、新增并发调用模式等）。
- **§4.3 Reviewer 产出要求**：合同前提保护的 finding 仍须填写 `review 建议`（说明若用户违反前提会触发的后果），但作者侧应直接以合同为由拒绝修复。
- **§6 历史归档规则**：`关闭-已拒绝` 的合同前提保护 finding 永久保留在主 review 文件中，不归档。

#### 4.4.7 示例

**示例 1：合同前提保护（合法关闭）**

```markdown
### BROKER-001: `g_broker` 是 plain pointer，与 shutdown 竞争

- **状态**: 关闭-已拒绝
- **关闭原因**: 合同前提保护：`ns_broker_add`/`ns_broker_remove` 在
  `src/ns_broker.c:20` 文件头注释明确文档化
  "*ns_broker_add / remove 与 ns_shutdown 不能并发调用*"。
  finding 所述的"shutdown 期间另一线程缓存 g_broker 导致 UAF"仅在
  调用方违反该前提时出现。属用户错误而非库缺陷。
- **关闭日期**: 2026-07-04
```

**示例 2：应作为真实 bug（不构成合同前提保护）**

```markdown
### BROKER-014: `ns_broker_global_init` 在并发 init 之间存在 TOCTOU

- **状态**: 打开  ← 不应被合同前提保护关闭，因为公共头未文档化
                 "init 必须单线程"
```

**示例 3：前提未文档化（应转为文档缺陷）**

```
finding 描述：consume_fn 内调用 ns_broker_add 会死锁
公共头 nanosig_broker.h 中的 consume_fn 注释：
  /* consume_fn 由 broker loop 线程调用 */
未出现"禁止调用 add/remove"字样。
→ 合同前提保护**不成立**，应作为真实 finding 或先文档化再决定。
```

## 5. 状态变更流程

```
[Reviewer 发现] → 写入"现在打开的问题"（状态=打开）
       ↓
[作者实现修复] → 移入"修复历史"，引用修复 commit
       ↓ 或
[作者评审拒绝] → 移入"现在关闭的问题"（状态=关闭-已拒绝），不可删除
       ↓ 或
[双方协商延期] → 移入"现在关闭的问题"（状态=关闭-延期），附目标版本
```

任何状态变更**必须在 commit message 或 review 注释中说明**。

---

## 6. 历史归档规则

- `关闭-已拒绝`：**永久保留在主 review 文件中**，从不归档
- 其他 `关闭-*` 状态：关闭满**一个月**后由 review agent 自动移至历史归档
- 归档流程（review agent 执行）：
  1. 扫描 `docs/review/*.md` 中"现在关闭的问题"分区
  2. 找出所有 `关闭-已修复`/`关闭-延期`/`关闭-不适用` 状态且关闭日期满一个月的条目
  3. 从主 review 文件中**删除**这些条目
  4. 将删除的条目**追加**到对应的历史归档文件

### 6.1 历史归档目录结构

```
docs/review/
├── AGENTS.md
├── ringbuf-code-review.md          # 主文件（修复历史 / 打开 / 关闭）
├── ...
├── history/                        # 历史归档目录
│   ├── ringbuf/
│   │   └── ringbuf-archive-2026-07.md
│   ├── timer/
│   │   └── timer-archive-2026-07.md
│   ├── ...
│   └── global/
│       └── global-archive-2026-07.md
```

- 每个模块一个子目录：`history/<模块名>/`
- 归档文件名格式：`<模块名>-archive-<年>-<月>.md`
- 按**月**分文件：同一个月内的多次归档追加到同一文件

### 6.2 归档文件格式

```markdown
# Ringbuf — 已归档问题
```

### 6.3 Review Agent 自动化

- review agent 是一个专用 agent，被周期性触发或手动调用
- 每次运行产出**一次 commit**，不允许批量产生多个 commit
- 单次 commit message 格式：
  ```
  review(history): 归档已关闭超过一个月的 N 条问题

  - TIMER-003 → docs/review/history/timer/timer-archive-2026-07.md
  - RINGBUF-009 → docs/review/history/ringbuf/ringbuf-archive-2026-07.md
  - BROKER-002 → docs/review/history/broker/broker-archive-2026-07.md
  ```
- review agent 不修改主 review 文档的"修复历史"或"打开问题"部分
- 主 review 文档中 `关闭-已拒绝` 状态的条目永不触及

## 7. 写作风格

- 严重度标识必须使用 emoji：`🔴` `🟠` `🟡` `🟢`
- 问题 ID 必须在每条记录的标题行
- 代码引用必须使用 `file_path:line` 格式
- 失败场景必须**具体可重现**：给输入、给状态、给观察到的输出
- "作者建议"必须**可执行**：描述具体修复方向或代码改动，而不是泛泛"应改进"

---

## 8. 与现有文件的兼容性

- 本规范**对历史 review 文档不追溯生效**
- 新编写的 review 文档必须按本规范
- 现有 review 文档（ringbuf, timer, mpsc-record-ring, hashtable, rbtree, broker, nanosig-core, platform-ports）可在下次更新时迁移到新结构
- 迁移时按问题 ID 重新编号，并补充缺失的"作者建议"与"关闭原因"字段
