# Implementation Plan: nanosig 信号槽/Timer/Broker 测试方案

> Source spec: `.omc/specs/deep-interview-signal-timer-broker-test-plan.md`
> Status: **pending approval** — revised after Architect + Critic consensus review (Iteration 1)

## Requirements Summary

基于 deep-interview spec 产出两层测试代码：

1. **单元测试补全**（`test/unit/`）：填补 P9 审计列出的 Critical + Major + Minor 测试缺口
2. **集成测试**（`test/integration/`）：15 个独立的自验证场景，复杂组合信号槽/Timer/Broker

优先级：先单元测试补全 → 后集成测试。

## RALPLAN-DR Summary

### Principles
1. **零第三方依赖**：延续当前手写 EXPECT 宏 + main() 串行模式，不引入 CUnit/Unity/CMocka
2. **可复现确定性**：所有测试要么精确验证（assert），要么输出定量统计（timer jitter），不接受模糊的"应该可以"
3. **渐进实施**：P9 单元测试缺口 → Layer-1 基础集成 → Layer-2 压力 → Layer-3 行为验证，每层可独立 CI
4. **内存安全优先**：每个测试都必须在 ASAN 下通过，集成测试额外保证 LSAN 零泄漏和完美退出
5. **跨平台一致**：所有测试代码在 macOS/Linux/Windows 三平台有相同语义

### Decision Drivers
| Driver | Weight |
|--------|--------|
| D1: 最小化对现有代码的侵入 | High |
| D2: 测试可维护性和可读性 | High |
| D3: CI 运行总时长可控 | Medium |

### Options

#### Option A: 原地扩展 + 按层分组集成测试（推荐 — 修订版）
- 单元测试直接在 `test/unit/test_{signal,timer,broker}.c` 末尾追加用例
- 集成测试放在 `test/integration/test_integration_{slug}.c`，按 Layer 合并为 **4 个 CMake 目标**（Layer-1、Layer-2、Layer-3 各一个，**群蜂归巢**独立保留以实现单独 TIMEOUT）
- 共享 `test/integration/integration_helpers.h` + `test/test_macros.h`
- **Pros**: 最小化工程改动，按层分组减少 CMake 目标数（15→4），长稳测试仍可独立设置 TIMEOUT
- **Cons**: 层内各场景共用 TIMEOUT，层内一个测试失败需重跑整层

#### Option B: 一个集成测试主程序 + 场景子函数
- 所有集成场景在同一个 `.c` 文件中，`main()` 调用各场景
- **Pros**: 单个 CMake 目标，编译快
- **Cons**: 违背"一个场景一个 demo"的用户要求，长稳场景和快速场景混在一起

#### Option C: 使用现有 CTest 的 `FIXTURES_REQUIRED` 模式
- 利用 CTest Fixture 做 setup/teardown
- **Pros**: CTest 原生支持依赖管理
- **Cons**: 增加了 CMake 复杂度，现有工程无此模式，侵入大

**Invalidation rationale for rejected options:**
- **Option B**: 违背用户明确要求"一个场景一个 demo"，且 20 分钟长稳测试和 30 秒空转测试不应绑定在同一个可执行文件中
- **Option C**: 过度工程，CTest Fixtures 在此场景没有显著收益

## Architecture Decisions

### ADR-001: 测试目录结构（修订版）

**Decision**: 采用 Option A 修订版 — 原地扩展单元测试 + `test/integration/` 独立目录，按 Layer 合并 CMake 目标
**Drivers**: D1 (最小侵入), D2 (可维护性), D3 (CI 时长)
**Alternatives considered**: 15 个独立目标（原始 Option A）, 单一集成文件 (Option B), CTest Fixture (Option C)
**Why chosen**: 
- 用户明确要求"一个场景一个 demo" — 每个场景在物理上保持独立 .c 文件
- 但 15 个独立 CMake 目标对嵌入式友好库过于膨胀（Critic 第 6 节钢人反驳）
- 折中方案：物理文件保持独立（便于维护），CMake 目标按 Layer 分组（减少构建膨胀）
- 长稳测试（群蜂归巢）保留独立 CMake 目标以支持单独 TIMEOUT 1500
**Consequences**:
- 正面: 仅 4 个 CMake 目标（vs 15），构建时间减少约 70%；长稳仍可独立超时；场景文件仍独立易于维护
- 负面: 层内各场景需要共享 `main()` 入口 → 通过命令行参数或编译时宏选择场景
- Mitigation: 每个场景文件提供独立 `run_scenario_xxx()` 入口函数，层聚合文件通过函数指针数组调度

### ADR-002: 测试框架增强

**Decision**: 将 `EXPECT_OK` / `EXPECT_EQ` 从各文件复制提为共享头文件 `test/test_macros.h`
**Drivers**: D2 (可维护性)
**Alternatives considered**: 引入 CMocka, 保持现状逐个文件复制
**Why chosen**: 三份重复的 EXPECT 宏（signal/timer/broker）已经出现代码异味，15 个集成测试若再每个复制一遍完全不可接受
**Consequences**:
- 正面: 消除代码重复，新测试文件引入 EXPECT 宏的成本降为 0
- 统一格式：`EXPECT_EQ` 一律使用 `%lld` + `(long long)` — signal 测试原用 `%d` 会在 64 位平台截断 `size_t`/指针值

### ADR-003: `test/` 头文件体系

**Decision**: 建立三层头文件体系：
- `test/test_macros.h` — 通用 EXPECT 宏（从各 .c 提取）
- `test/test_helpers.h` — 平台 waitable helpers（从 `test/unit/test_helpers.h` 迁移）
- `test/integration/integration_helpers.h` — 集成测试专用 helper（新建）

**Drivers**: D1, D2
**Why chosen**: 
- `test/unit/test_helpers.h` 的跨平台 waitable 函数也完全适用于集成测试，不应重复
- 迁移路径：新建 `test/test_helpers.h`（原内容）→ `test/unit/test_helpers.h` 改为 `#include "../test_helpers.h"` → 更新 `test_broker.c` 引用
- CMake 中 `nanosig_add_unit_test()` 添加 `target_include_directories(${name} PRIVATE ${PROJECT_SOURCE_DIR}/test)`，使 `#include "test_macros.h"` / `#include "integration_helpers.h"` 可直接工作

### ADR-004: Broker Error 注入点

**Decision**: 在 `src/ns_broker.h` 和 `ns_broker.c` 中添加 `#ifdef NANOSIG_TEST` 保护的测试注入点
**Drivers**: D1 (最小侵入)
**Alternatives considered**: weak symbol override, 全局 hook 指针
**Why chosen**: 
- Weak symbol 是 GCC/Clang 扩展，MSVC 不支持 → 三平台不可移植
- 全局 hook 指针在非测试构建中占用不必要的 8 字节
- `#ifdef NANOSIG_TEST` 在 Release 构建中零开销，三平台一致
**Implementation**:
```c
/* ns_broker.c — 第 187 行附近 */
#ifdef NANOSIG_TEST
    /* Test hook: test can set this to inject waitset_wait failures */
    int g_ns_test_waitset_wait_result = NS_OK;
#endif
    int rc;
#ifdef NANOSIG_TEST
    if(g_ns_test_waitset_wait_result != NS_OK){
        rc = g_ns_test_waitset_wait_result;
    } else {
        rc = ns_platform_waitset_wait(...);
    }
#else
    rc = ns_platform_waitset_wait(...);
#endif
```
测试编译时加 `-DNANOSIG_TEST`，设置 `g_ns_test_waitset_wait_result = NS_E_INVAL` 后调用 `ns_init()`，然后验证 broker 线程仍在运行（通过创建可触发的 watcher 确认）。

### ADR-005: CI 测试分组策略

**Decision**: 使用 CTest LABELS 属性实现测试分组
**Drivers**: D3 (CI 时长)
**Why chosen**: 修复原计划的 bug（`ctest -R integration-` 因下划线命名匹配 0 个测试）
**Implementation**:
- 所有集成测试标记 `LABELS "integration"`
- 长稳测试（群蜂归巢）额外标记 `LABELS "integration;long-stability"`
- CI 使用 `ctest -L integration -LE long-stability` 排除长稳
- Nightly 使用 `ctest -L integration` 全量运行
- 或在 CMakeLists.txt 中添加 `option(NANOSIG_BUILD_LONG_TESTS "Build long-stability tests" OFF)`，CI 关闭，nightly 打开

### Step 7: 创建集成测试基础设施

**Actions**:
1. 创建 `test/integration/` 目录
2. 创建 `test/integration/integration_helpers.h` — 集成测试公共 helper：

static int scenario_xxx(void)

**每个场景的 MPSC 容量计算依据：**

#### Layer-1 场景容量计算：
| 场景 | 需要容量 | 计算依据 | 分配 |
|------|---------|---------|------|
| 群蜂归巢（独立） | max 同时~220 emits × 8 bytes = 1,760B | 200 timer + 20 watcher，安全余量 ~37× | `NS_CAPACITY_65536` |
| 级联信号链 | 线性10级+分支5，最多~15 emits | 串行触发，burst 极小 | `NS_CAPACITY_16384` |
| 看门狗模式 | ~3 emits 同时 | 只 2 个 watcher + 1 timer | `NS_CAPACITY_8192` |
| 双 Loop 桥接 | ~2 emits 同时 | 串行 emit | `NS_CAPACITY_16384` |
| 生命周期混战 | ~11×8=88B | 最多 5 watcher + 3 timer + 额外操作 | `NS_CAPACITY_32768` |

#### Layer-2 场景容量计算：
| 场景 | 需要容量 | 计算依据 | 分配 |
|------|---------|---------|------|
| 定时器风暴 | 5000×8=40KB (15.3%) | 5000 timer 同时触发 | `NS_CAPACITY_262144` (256KB) |
| 混沌测试 | ~10×8=80B (0.1%) | 随机操作峰值较低 | `NS_CAPACITY_65536` |
| 信号风暴 | 1000×8=8KB (3.1%) | 1000 次 emit | `NS_CAPACITY_262144` (256KB) |
| 重入竞态 | ~20×8=160B (0.2%) | 8 线程 emit + 回调内操作 | `NS_CAPACITY_65536` |

#### Layer-3 场景容量计算：
| 场景 | 需要容量 | 计算依据 | 分配 |
|------|---------|---------|------|
| 多 Loop 路由 | ~50×8=400B (2.4%) | 3 loop 交叉 emit | `NS_CAPACITY_32768` |
| 精度与过载 | ~25×8=200B (1.2%) | 5 repeat timer + 少量 emit | `NS_CAPACITY_16384` |
| 鸡尾酒派对 | 4 types × 500 × (~8+1024+B)=~2MB | 大 payload (1024B) 是关键——每条记录≈1064B | `NS_CAPACITY_2097152` (2MB) |
| 空转无泄漏 | 0 | 无 emit | `NS_CAPACITY_1024`（默认） |
| 多 phase 长跑 | ~50×8=400B | 分阶段加卸载 | `NS_CAPACITY_16384` |
| 资源清理验证 | 0 | 无 emit | `NS_CAPACITY_1024`（默认） |

#### 场景实现关键点：

**7a. `scenario_hive.c`** — 群蜂归巢（独立目标 `test_hive.c`）
- 20 fd watcher + 200 随机 timer（1ms-5s）
- 使用 `ns_loop_start/stop` 后台运行模式（详见 7d Idle 修复模式）
- 每 30 秒打印进度
- 20 分钟后验证 timer 触发计数，输出统计
- **容量**: `NS_CAPACITY_65536`（安全余量 ~37×）

**7b. `scenario_cascade.c`**
- Timer cascade：线性链 depth 10 + 分支链（1→5）
- 使用 `ns_timer_restart` 在 slot 中启动下一级 timer
- 因果验证：每个阶段触发次数 = 1

**7c. `scenario_watchdog.c`**
- Watchdog timer（1s 周期）轮询 watcher 活动计数器
- 2 fd watcher，其中一个自动停活后被 watchdog 移除
- 输出详细 phase 标记

**7d. `scenario_dual_loop.c`**
- Loop-A（IO 线程，`ns_loop_start`） + Loop-B（IO 线程，`ns_loop_start`）
- 验证跨 loop emit 100 次

**7e. `scenario_lifecycle_chaos.c`**
- 随机操作线程（每秒：add/remove/disconnect/reconnect/timer_cancel/restart）
- 5 watcher + 3 timer 同时运行
- 运行 10 秒后停止，验证 0 crash

**8a. `scenario_timer_storm.c`**
- 5000 timer，间隔 100μs-1ms，全部 100ms 内启动
- 使用 `ns_loop_start/stop`（后台线程不影响 timer 启动）
- 输出延迟统计 p50/p99/max
- **容量**: `NS_CAPACITY_262144`

**8b. `scenario_random_chaos.c`**
- 工作线程交替 emit/disconnect/add/remove/cancel/restart
- 每秒记录操作分布
- 5 秒运行，验证 0 crash

**8c. `scenario_signal_storm.c`**
- 1 signal → 50 slot（分属 2 个 loop）
- 4 个线程各 250 次 emit = 1000 次总量
- 验证每个 slot 收到 1000 次 → 累计 50000
- 计数使用原子操作，非 volatile
- **容量**: `NS_CAPACITY_262144`

**8d. `scenario_reentrant_race.c`**
- 8 线程同时向同一个 loop emit 同一个 signal
- Slot 回调内随机调用 broker_add/remove/timer_start/cancel
- 使用 `ns_platform_barrier`（如 pthread_barrier_t）同时启动所有线程
- 使用条件等待的超时模式（非 spin-loop）

**9a. `scenario_multi_route.c`**
- 3 loop (A/B/C)，各运行在一个后台线程
- Chain：watcher-1 → signal S1 → loop-A → emit S2 → loop-B → emit S3 → loop-C
- Fan-in: 3 watcher → 1 signal
- Fan-out: 1 signal → 3 slot × 3 loop
- 使用 `integration_wait_for_condition()` 验证路由正确性

**9b. `scenario_timer_precision.c`**
- 5 个 repeat timer（100μs / 1ms / 10ms / 100ms / 1s）
- 每个 timer 记录实际触发时间戳
- 3 秒后输出统计（min/max/avg/jitter）
- 过载验证：1ms timer + 5ms handler → 不追赶
- **注意**：macOS 上 100μs 定时器受 kqueue 分辨率 ~1ms 限制，在 Linux 上测量精度，macOS 上仅做功能验证
- 精度统计使用 `ns_platform_clock_monotonic_us()` 而非 `gettimeofday()`

**9c. `scenario_cocktail.c`**
- 4 种 payload 类型：no-payload / int(4B) / small struct(24B) / large struct(1024B)
- 每种连接 3 slot，送 500 次 emit
- 大 struct payload 验证：data integrity（值未被篡改）
- **容量**: `NS_CAPACITY_2097152`（大 payload 场景——1024B × 500 = 512KB，安全余量 4×）

**9d. `scenario_idle.c`**
- 使用 `ns_loop_start/stop` 模式（修复：不使用 `ns_platform_sleep` + 独立线程）
- 解法：创建一个 31 秒的 oneshot timer 自动退出 loop
- 0 watcher 0 timer → start → idle 30 秒 → stop → shutdown
- 验证 LSAN 报告零泄漏

**9e. `scenario_lifecycle_marathon.c`**
- 4 phase × 每个 phase 30 秒：
  - Phase 1: 创建 5 timer
  - Phase 2: 创建 5 fd watcher
  - Phase 3: 混合（cancel/remove/add）
  - Phase 4: 逐步 shutdown
- 每 phase 结束打印 `[PHASE]` 和单轮资源计数
- 退出后 shudown → re-init → 重复，共 3 轮
- 内存增长验证：使用 `getrusage(RUSAGE_SELF).ru_maxrss` 比较每轮间的驻留内存峰值增量（不要求精确到字节，只验证无明显增长趋势）

**9f. `scenario_cleanup_verify.c`**
- 不独立运行：每个集成测试末尾已自带 `integration_verify_clean_shutdown()`
- 本文件仅提供 `integration_verify_clean_shutdown()` 的**跨场景测试**：创建最小实例，强制检查：
  - `ns_shutdown()` 返回 `NS_OK`
  - 各平台 handle/thread/mutex 被正确释放（由 ASAN/LSAN 保证）
- 逻辑已合并到 `integration_helpers.h` 中

## Risks and Mitigations

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| MPSC ring 容量估算不足导致集成测试偶发失败 | Medium | High | 每个场景标注明确容量并附计算依据（见 Step 7 容量表）；场景初始化时对 loop queue 断言 `free_capacity >= expected_max_used` 而非仅 `> 0`；发布构建中此断言由 `#ifndef NDEBUG` 保护 |
| broker_error_continue 测试需要代码注入 | High | Medium | 采用 `#ifdef NANOSIG_TEST` 方案（ADR-004），三平台零开销；测试编译时加 `-DNANOSIG_TEST` |
| 鸡尾酒测试大 payload (1024B × 500) 接近 2MB 容量边界 | Medium | Medium | 分配 `NS_CAPACITY_2097152`（2MB），安全余量 ~4×；测试中增加运行时警告 if `free_capacity < 25%` |
| macOS 上 100μs 定时器精度受限 | High | Low | 精度统计仅在 Linux 上有量化意义；macOS 上仅验证功能正确（定时器触发 + 不 crash） |
| 集成测试跨平台失败 | Medium | Medium | 平台差异已由 `test_helpers.h` 封装；CI 前在所有三平台验证 |
| 重入竞态测试偶发时序失败 | High | Low | 使用 `ns_platform_barrier` 同步启动而非 sleep；运行 3 次取一致结果；超时等待使用单调时钟 |
| 20 分钟长稳测试 PR CI 被误触发 | Low | Low | CTest LABELS "long-stability" 在 PR CI 中被 `-LE "long-stability"` 排除；仅 nightly 运行 |
| 测试宏提取后意外破坏现有测试编译 | Low | High | 分步操作：先复制宏到新文件，验证编译通过，再移除旧定义；CI 必须通过后才能合并 |

## Verification Steps

1. **编译验证（单元测试）**: `cmake --preset macos-debug-asan -DNANOSIG_BUILD_TESTS=ON && cmake --build --preset macos-debug-asan` 零警告
2. **单元测试验证**: `ctest --preset macos-debug-asan -R "nanosig_test_(signal|timer|broker|loop)" --output-on-failure`
3. **集成测试编译验证（无长稳）**: `ctest --preset macos-debug-asan -L integration -LE long-stability --build-no-clean`
4. **ASAN + LSAN 验证**: `ASAN_OPTIONS=detect_leaks=1 ctest --preset macos-debug-asan -L integration -LE long-stability --output-on-failure`
5. **MPSC 压力测试**: `ctest --preset macos-debug-asan -R mpsc_record_ring_stress --timeout 180`
6. **CI 筛选测试**: `ctest -L unit` (fast, <30s) + `ctest -L integration -LE long-stability` (medium, <5min)
7. **全量验证（含长稳）**: `ASAN_OPTIONS=detect_leaks=1 ctest -L integration --timeout 1800`
